# Companion consistency unit for the shared cloud save

This feature uses Accounts' identity and complete-save CAS/transport. It introduces no cloud account, inventory, reward endpoint or remote schema. Runtime-only API: `services.get('companions').backupAdapter`.

The adapter is `id: companions, version: 1`, with synchronous `export(owner)`, `validate(data, owner)`, `restore(owner, data, mode)`, `dataChecksum(owner)` and `fromLegacyTables(tables, owner)` methods. Its data is `{ownerAccountId, tables, identityImports}`. `tables` contains the complete existing `companion_accounts`, `companion_pets`, `companion_actions`, `companion_legacy_archive`, `companion_interactions` and `companion_capture_receipts` rows. `identityImports` contains historical `companion_identity_imports` rows whose target is this owner. Those archives confer no authentication authority; Accounts must still verify every alias independently.

Every pet keeps its original petId, template/resource reference, name/serial/origin, growth, desktop position/visibility/behavior/scale and three independent chat/battle/guard selections. Same-template pets are never combined. Captured and action receipts retain their original IDs, request hashes and result JSON. Raw legacy/archived 3D animals remain in saves/history without becoming active 3D resources.

Restore is one SQLite savepoint, composing with the complete-save outer transaction. A matching unit is idempotent. Merge into an empty unit is allowed; different nonempty units raise `COMPANION_BACKUP_CONFLICT`, preserving both. Complete replacement requires Accounts' verified owner, preview, local-checksum/CAS checks and before-restore archive. A pet's state must never be row-unioned with another device's receipts. Foreign owner/nested pet mismatches, duplicate keys and dangling selections/capture references are rejected. Existing identity-import rows belonging to another target cannot be overwritten.

## Accounts integration requirement

The adapter is now registered by the production companion feature against the shared BackupManager. Shared checkpoint `6435a13` adds `normalizeData(data,owner)` as an internal view only, after the original envelope checksum, provenance, verified identity and generic schemas/owners have been validated. It moves all six complete old tables into the unit for restore and fingerprinting, preserving the original file and immutable cloud checksum. Mixed module/generic copies and partial table groups fail. The adapter's `tables` claims all seven SQLite tables, and `legacyTables` names the six former generic tables. `fromLegacyTables(completeGenericTables, owner)` does not invent missing identity-import proof. Source owner strings are never blindly replaced by an Auth UUID.

Approved08 `8e5c735` was merged in `230e9b6`, retaining `meaningfulData`, `prepareProtected`, `cloudProjection`, original-file archiving, privacy redaction and `authority_pending`. The legacy normalization only wraps fingerprints/restore views; it does not replace the protected outgoing cloud document or authorize local economic state. Both garden and companion module row arrays have set-order fingerprints; message order remains meaningful.

When the old envelope has no companion module and none of its six tables, call the same converter: it returns a validated empty unit for archives from before this feature. Explicit complete replacement clears a stale `legacy_imported_at` marker, after which the restored Accounts raw legacy inventory can import its original pet IDs again. Merge into existing progress still conflicts. An envelope containing only part of the six-table group is rejected. Stable row order and companion digests use ordinal comparison, independent of OS locale.

After an atomic full-save restore, emit `accounts:save-restored` with the verified owner. Companions listens for that existing event to refresh its pages and reconcile desktop windows after commit. Authentication and resource download readiness remain with Accounts/Resources.

The approved identity checkpoint `f81008c` (implementation `ee36030`) is merged. Its `LingjingActor.ownerAccountId` is the stable text owner; `authUserId` and `deviceId` are separate identities and never replace a pet owner. A same-owner save needs no pet-ID rewrite. Existing pre-Accounts alias migration still requires main-process Accounts identity and a recorded `legacy-id` alias. If Accounts changes an identity's subject to the new Auth UID while linking a different legacy alias, it must publish an explicit verified-alias authorization adapter; renderer claims or username matching cannot weaken this check.

Legacy pet IDs are unique **within an owner**, not globally. Two unrelated original accounts can both own `pet-001`; the existing SQLite primary key is `(owner_account_id, pet_id)`. Shared cloud owned-pet indexes, chat/personal-history authorization and authority-fragment commits use the same `(owner, petId)` pair after approved08 `d57d383` / `45b857d`. No original ID is renamed to work around a collision. Two-owner backup and local SQL command tests cover this behavior; these are not cloud acceptance.

The shared protected-save policy correctly treats growth, capture/adoption receipts and inventory as authoritative. Legitimate rename, desktop position/visibility/behavior and independent selection changes still need an approved Accounts personal-field path that retains those protected values. A valid checksum alone cannot authorize adding pets, changing their original identity, granting growth, or replacing capture/reward history. This module does not add an alternative cloud endpoint to bypass that policy.

## Garden integration requirement

`garden/cloud-domain.mjs` currently reads `envelope.data.tables.companion_pets/accounts.rows`. For new saves, read the same rows from `envelope.data.modules.companions.data.tables.companion_pets/accounts`; keep complete old-format reads for migration. The inventory debit, pet effect, account revision and receipt must stay in the same authoritative locked complete-save transaction. Do not create a second pet, inventory or growth-reward store. Companions' local `applyGrowthInTransaction` remains the same shared-connection adapter.

`companions/cloud-growth.mjs` now exports the pure async `awardBattleResult({envelope,ownerAccountId,petId,sessionId,won,mode,actionId,now}) -> {envelope,reward}` requested by05. It performs no HTTP, DB write or commit.05 must first verify the08 actor and finished server battle, then commit the returned companion unit with its inventory/world changes in one protected authority transaction. The action ID must be `battle:<sessionId>:<owner>`; win/loss, pet and session bind the receipt. Matching old local growth receipts are recognized, and retries do not add XP or wins. The function handles the complete new module or complete retained generic format, without mixing them.

Domain action/receipt IDs accept up to512 characters with control characters rejected, retaining original long `battle:<session>:<owner>` values. Owner, pet, session, operation and name limits stay unchanged. Public CAS keys retain their separate contract. The160-character original-owner /51-character session regression passes through the actual shared growth function, backup validation and another SQLite restore in both module and complete legacy formats; it never renames an original receipt.

SQLite `CompanionsService.applyEffect` and this cloud adapter both use `growth.mjs.applyGrowthEffect`:100 XP per level, +10% stats, existing caps and validation. The existing battle participation policy remains20 XP for a win /5 for a loss. Only a verified domain result selects that effect; the adapter rejects caller-provided XP. Other pets, positions, names, independent choices and raw archives remain unchanged. Appended receipts use the same PK row order as the local adapter for stable full-save readback.

The controlled `companions-sync` command entry covers adoption, rename, independent selections, desktop settings, authorized appearance, fixed server-clock interaction and recall-all. Production IPC now invokes it through08 `cloudActor`. `CloudCompanionAuthority` journals command intents and verified head metadata in the existing `account_actions` table before network I/O; it introduces no second account, pet, inventory or remote save store. After every command it independently reads the exact immutable common receipt and the latest companion snapshot before restoring the complete companion unit in one SQLite savepoint. It advances the common Accounts base only if08's strict full-save comparison succeeds; other pending modules remain preserved and are reported as `sharedSavePending`.

Main APIs `select(owner,input)` and `recallAll(owner,actionId)` return a Promise for Supabase sessions. Consumers must await the result before changing chat/battle/guard preferences or showing success. `refreshCloud(owner)` resumes original pending requests; `applyCloudReadback(owner,remote)` accepts the verified companion snapshot shape `{authority:'live',ownerAccountId,revision,envelope,module}`. Cloud capture and growth consumers must use their verified domain settlement/readback; `createCapturedInstance` and `applyGrowthInTransaction` reject a local protected write during a Supabase session. Local-only accounts retain their existing synchronous behavior.

Native drag/wander persistence also uses this command path. Unknown sent requests retain the original actionId, payload, input hash and base revision across restart. Only position drafts that have never been sent may be superseded by a newer position. A pending recall-all hides native windows while its receipt is unconfirmed. Local unverified historical progress cannot be silently overwritten by an empty or different cloud unit; original pet IDs, action receipts and archives must remain present when a verified unit advances.

## Verification boundaries

`tests/cloud-authority.test.cjs` contains six explicitly labelled protocol simulations using actual SQLite, the shared BackupManager/AccountSync and production command reducers. They cover offline-before-send restart, committed-but-unacknowledged adoption, immutable sent positions plus draft coalescing, old-progress/account-switch preservation, unrelated offline notes/common requests, and a cached original-action replay queued across an account switch. The queue checks the verified owner both before executing and before returning, including cached replays. The final focused run also includes Accounts-boundary and playback isolation (eight tests passed). This is not HTTPS or Electron evidence; those acceptance steps remain separate.

The seven `tests/backup.test.cjs` cases use independent real SQLite files and product domain code, including verified alias/history preservation, archives from before companion tables and two owners retaining the same original pet ID. `tests/backup-integration.test.cjs` registers the unit with the actual Accounts BackupManager and Garden adapter: complete restore transfers food, exactly one pet's growth and both replay receipts; an injected later-adapter failure rolls everything back. This explicit test registration does not claim that production legacy conversion is already delivered.

`tests/backup-desktop.acceptance.mjs` uses production Electron44/IPC/Accounts restore, fresh path-bound QA profiles and read-only SQLite inspection. It tests restoring a disconnected monitor position at the same pet revision, the five-second save timer, a process restart and intentional drag persistence. Both opening a restored pet and updating an existing window derive local bounds without saving the monitor clamp. These are local preservation/transaction/native tests, not live-cloud evidence. Real HTTPS identity, two-device save CAS and deployed inventory readback remain required after the coordinator publishes the shared contracts and deployment. Existing 2D and Accounts' 1–4 visible-companion contract stay unchanged.

The deployed companion command chain now has actual default-entrypoint Electron acceptance: `tests/cloud-native.acceptance.mjs` passed seven groups at55d6b24, including two independent device/userData roots, receipt replay, concurrent rename, native drag, A-only TLS refusal, original-position recovery after process restart and verified custom2D availability/pixels in B. `tests/cloud-native-restart.acceptance.mjs` passed five targeted groups on frozen4830619 plus the queued-owner guard (9a18511), recording actual Electron PIDs, loaded guard function hashes, encrypted-session resume, cached adoption replay, fixed interaction replay and both specified custom-resource native frames. `tests/cloud-recall.acceptance.mjs` separately verifies the registered main recallAll capability and an independent real HTTPS receipt in a lightweight Node host; it makes no native tray or full-save advancement claim. See `evidence/companions/cloud-2026-10-25/README.md` for source/run identities and retained failed verifiers. All of these clients ran on one physical Windows host.

The shared checkpoint fixture now registers the production companion unit and supplies the current session capability. Its assertions retain strict `CLOUD_LOCAL_CONFLICT`, `SYNC_PENDING` and `SYNC_BUSY` checks on Accounts, and verify the original pending request is unchanged. A verified domain readback may preserve unrelated offline notes while applying that domain; it cannot advance the complete-save base until Accounts accepts the whole snapshot. These are local real-SQLite tests, not additional HTTPS claims. Original external old-cloud data cannot be called migrated without its verified source; local old files, aliases and histories remain independently covered and preserved.
