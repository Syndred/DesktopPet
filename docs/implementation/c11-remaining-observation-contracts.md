# C11 remaining observation contracts

These contracts prepare assertions for two unexecuted parts of C11. They are not
login runners, authorization capabilities, collectors, or authenticated evidence.
They consume a deliberately narrow projection of future observations. Synthetic
tests show that those projections are checked consistently; they do not show
that any real account transition or allocation occurred.

The existing discovery runner remains unchanged. The two relevant `uncovered` entries and
`fullCasePassed: false` remain in place. Passing either observation contract must
not remove an acceptance gap or promote the overall case.

## Same original profile: A to B to A

The product supports ordinary logout and login in one profile. Its device ID is
profile-owned, while cloud device bindings are keyed by owner and device. The
current fixed test holder intentionally does not permit this transition: role
`a` is bound to A and the five-role business guard requires each original actor.
The existing C/A15 transition capability is not reusable for A or B.

A future runner needs a separately reviewed one-use C11 transition capability
and a bounded grant for B on the original A device, without replacing any of the
five original grants. Before starting it must also verify the current run's
authorization, credential custody, owned process registry, watchdog and deadline.
None of these prerequisites is created by an observation object.

The observations must preserve the original profile and processes, original
device, run and commit. They must record the ordered A, signed-out, B,
signed-out, A states, confirmed normal logout results, correctly advanced epochs,
fresh sessions, unchanged peer bindings, and the separate B-on-A-device grant.
The B view must contain B's original identity and exclude A's captured instance.
The final A view must show the exact original owner, pet, template and number
after a fresh ordinary cloud readback. A cached number or a visible login form
alone is insufficient.

The future transition must restore the discovery hook before logout and dispose
the old session-bound location fixture. After returning to A it must restore the
unchanged full business guard and create any new UI binding through its existing
authorized path. Unknown logout or login outcomes must not be blindly retried.

## A second template's own sequence

The product allocator is keyed by namespace and template. The existing sealed
concurrent evidence covers only `animal-wood-deer` numbers 4 and 5. The current
`wild-only` completion flow does not issue two new adoptions for another template.
A fallback wild encounter of a different template is not this missing sequence.

A future explicitly scoped pair of ordinary adoptions can supply the missing
observations. Each original action ID and input must be retained, and each actual
success receipt must identify its owner, pet and chosen template. The ordinary
cloud snapshot's separately returned serial registry must bind that same pet to
the same existing namespace and canonical number 1, then 2. The UI must display
0001 and 0002. The sealed deer 4/5 references establish that this is a different
template's sequence, not a new namespace or a reset of the original sequence.

The original adoption receipt need not itself contain a number. Never invent
that field or derive a starting point from the highest pet visible to A or B.
Owner snapshots omit other owners and uncaptured assignments. Two new ordinary
actions require an explicit bounded execution plan; this preparation neither
adds those actions nor authorizes them.

No private global-counter read is required by this original acceptance step.
Stable deer pet mappings must not be described as proof that the whole deer
counter did not change. A fresh namespace, reset counter, edited historical
receipt, or changed original action is not an acceptable substitute.

## Runtime evidence boundary

The observation validators intentionally do not authenticate source material.
A future collector must retain the original receipts and exact source bindings,
verify its real authorization before every action, and record failures honestly.
The validators' fixed result explicitly remains assertion-only, unauthenticated
as to source, and not a full-case pass. They have no network, SQL, file, process,
credential, or business-action API.
